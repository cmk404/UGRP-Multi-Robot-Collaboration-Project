# 구역 상자 4색 RGB 검출 (교사 실행기 교체 1단계)

작성 2026-09-25. 브랜치 `claude/zone-rgb-color`. 검출기·평가 소스 `881b356`(렌더·채점 모두 깨끗한 트리). 원자료는 로컬 전용 `outputs/zone-rgb-color-20260925/`(기본 체크아웃, gitignore)에 있다. 원격 백업이 아니다.

## 질문과 범위

지금 구역 벤치마크(ZC1/ZC2, `zones/zone_wide`)는 정답 좌표로 움직이고 잡는 **교사 실행기**를 쓴다. 이를 RGB 스킬로 바꾸는 순서는 (1) 색 검출 → (2) TOP 네 대로 위치 추정 → (3) 정적 지도 이동·배치 → (4) 교사 없는 양보다. **이 기록은 (1)만 다룬다.** 각 로봇의 자기 RGB와 TOP RGB에서 네 색(청록·초록·빨강·노랑) 상자를 찾을 수 있는지, 오프라인에서 잰다.

- 제어 경로에 연결하지 않았다. 구역 실행의 이동·파지·배치는 여전히 교사다. 이 결과는 RGB 스킬 성공이나 배송 성공이 아니다.
- 평가 장면은 `zones/zone_wide`만 쓴다(코디네이터 지시: ZC1/ZC2가 zone_wide, `zone_open`은 퇴역 대상). dev 반복 중 잰 `zone_open` 수치는 버렸고, test를 만들기 전에 분할에서 뺐다.
- `dispatch/open`은 빔 혼동을 보는 **부록**이다. 구역 장면은 빔을 숨기므로(`rgba 0`) 구역 수치에는 빔이 없다.

## 기존 인식 (조사 결과)

| 경로 | 위치 | 하는 일 | 한계 |
|---|---|---|---|
| 자기 RGB, 청록 1개 | `harness/markerless_box.py::observe_ground_box` (RGB 실행 번들 v61 소스) | HSV H73–104·S≥65 실루엣 → 발행한 팔 펄스로 계산한 카메라 자세 + 어안 모델로 알려진 직육면체를 바닥에 투영해 IoU≥0.58이면 받아들임. 윗면 사각형 경로도 있음 | 청록 전용. 후보가 둘 이상이면 "구분 불가"로 거절. 바닥 접점이 카메라에서 1.2 m를 넘으면 적합하지 않음 |
| TOP, 4색 | `harness/zone_perception.py::detect_boxes` (ZC1/ZC2 러너가 사용) | 색별 HSV 범위, 면적 30–260 px, **축 정렬 bbox 채움 ≥0.55**, 종횡비 ≤2.2, 작성된 TOP 보정으로 바닥 좌표 | 자기 RGB 없음. 평가 기록 없음 |

카메라: 로봇 `robot_cam`은 팔에 달린 어안(960×720, 핀홀 렌더를 `raw_fisheye_remap`으로 변환), TOP은 높이 2.5 m·FOV 55° 아래 방향 네 대(`TOP_SW/NW/SE/NE`)이며 상자 윗면이 약 10×11 px로 보인다. 상자는 원래 청록 상자와 모양·질량이 같고 칠만 다르다(`sim/zone_arena.py::COLORS`). 헷갈리기 쉬운 것: 적재 구역 파랑 칠(H100–110, 청록 상한 H104와 겹침), 구역 A 주황 칠(H11–13), 구역 C 보라 칠(H142), 로봇 노랑 메카넘 롤러(TOP에서 H≈25, 노랑 상자와 HSV가 같음), dispatch 주황 빔(H13–21)과 노랑 대기선 칠(H19–23).

## 바꾼 것

- `harness/zone_color_boxes.py` (새 파일, 번들 소스 closure 밖): `detect_own(image, 발행 팔 펄스, kinds, profile)`, `detect_top(jpeg, TOP 보정, kinds, profile)`. 입력은 RGB와 자기 발행 명령·작성 보정뿐이다.
  - 기본 프로필은 기존 동작이다. `own_production_v1`: 청록은 `markerless_box._cyan_components`를 그대로 호출하고, 나머지 색은 같은 형태 게이트에 dev에서 정한 HSV 범위를 쓴다. `zone_perception_v1`: `zone_perception.detect_boxes` 그대로.
  - 선택 프로필(명시해야 켜짐): `own_zone_v2` = 적재 칠을 뺀 청록 범위(H85–98, S≥120) + 1.2–4 m 원거리 거친 적합(`range_class='far_coarse'`, IoU≥0.50). `top_zone_v2` = `minAreaRect` 기반 회전 불변 채움 ≥0.70·종횡비 ≤2.2, 3×3 닫기, 면적 50–300 px, dev 통계로 정한 범위.
  - `markerless_box.py`·`zone_perception.py`는 바꾸지 않았다(테스트가 v61 번들 해시와 비교).
- `scripts/eval_zone_color_detection.py` (작업 흐름 `zone-color-eval` 등록): `render`는 표준 `ZoneScene`으로 장면을 만들고, 로봇·상자를 다시 놓고(팔 0.3 s 이동 + 0.3 s 안정화, 동기 SIM) 로봇 입력(`frames/`: 자기 RGB·TOP JPEG·발행 팔 펄스)과 **평가 전용 정답**(`eval-labels/`: 자세·분할 영상·가시 비율)을 따로 쓴다. `score`는 검출기를 `frames/`에만 돌린다.
- 장면 사례(시드당 13): layout(초기 격자)×2, approach(목표 앞 0.14–0.5 m, 60%는 다른 색 상자 1–2개를 5.5–8.5 cm 옆에)×4, zones(구역 칸 위 상자)×2, edge(시야 가장자리)×1, occluded(다른 로봇이 사이에)×2, under_gripper(팔을 상자 위 9.5 cm에)×1, empty(빈 바닥·구역 칠·로봇만)×1. 카메라·외관·칠은 바꾸지 않았다.
- 분할(`split.json`, test 렌더 전 고정): dev = zone_wide 101–106 (+ dispatch/open 171–172), test = zone_wide 201–210 (+ dispatch/open 271–273). 임계값은 dev에서만 정했고 test는 `881b356`으로 한 번 렌더·채점했다.

## 실패 유형

1. **TOP 형태 게이트** (test zone 미검출 57개 중 37): 옆면이 보이거나 음영이 진 상자는 채움 <0.70이 된다. 청록이 가장 많다. baseline은 여기에 더해, 20° 넘게 돌아간 상자를 축 정렬 bbox 채움 게이트에서 대부분 놓친다(dev 미검출의 약 40%).
2. **TOP 작은 blob** (15): 로봇 옆 상자나 팔 아래 상자(under_gripper)는 50 px 미만으로 줄어든다. 같은 색 상자가 붙으면 한 blob으로 합쳐진다(2).
3. **노랑 롤러**: 메카넘 롤러는 TOP에서 노랑 상자와 색이 같다. baseline에서 14건. zone은 면적·채움으로 test 0건이지만 색 단서로는 구분하지 못한다. 롤러가 크게 보이는 시점에는 다시 생길 수 있다.
4. **자기 RGB 원거리**: 기존 적합은 1.2 m를 넘으면 받지 않는다(baseline 0%). zone의 `far_coarse`는 방향이 정확하다(dev 중앙 0.17°, p90 0.43°). 하지만 거리가 체계적으로 길다(중앙 +0.40 m, +21%). 발행 팔 펄스로 구한 카메라 기울기 오차 등이 원인 후보이며 확인하지 않았다. 원거리 결과는 "방향 + 대략 거리"로만 써야 한다.
5. **자기 RGB 청록 + 적재 칠**: 기존 청록 범위(H≤104)는 파랑 적재 칠을 섞어 상자를 잘린/큰 blob으로 만든다(baseline 근거리 청록 36/49). 기존 동작은 유지했고, 구역용으로는 `own_zone_v2` 범위를 쓴다.
6. **부분/가림**: 두 프로필 모두 약 40%(자기 RGB)와 50–70%(TOP)에 그친다. 화면 경계에 걸린 상자는 설계상 거절한다(기존 청록 경로와 같다).

## 한계

- 순간이동 재배치, 고정 조명·칠·해상도. 흔들림·들린 상자·실물 카메라 잡음은 없다. 실제 로봇 주행 중 프레임이 아니다.
- 색은 종류만 알려 준다. 같은 색 상자끼리의 개별 ID는 추적하지 않았다(2단계 과제).
- 원거리 거리 편향은 원인을 확인하지 않았고 보정하지 않았다.
- dev 임계값 선택은 dev 78장면에 맞춘 것이다. test는 같은 경기장·같은 사례 생성기라 새 지도나 조명으로 일반화된다는 근거가 아니다.
- 테스트 고정 조각(`tests/fixtures/zone_color/`)은 dev-r1(커밋 전 소스, 같은 프레임)에서 잘랐다.

## 2단계 제안 (TOP 네 대 위치 추정)

1. `detect_top(profile='top_zone_v2')`와 `detect_all`식 병합으로 매 관측 시점에 색별 바닥 좌표(test 중앙 3 mm, p90 8 mm)를 만든다. 같은 색은 이전 추정과 최근접 대응(작성된 칸·적재 격자를 사전으로 사용)으로 ID를 잇는다. 게이팅 반경과 "들고 있음/가려짐" 상태를 둔다.
2. 로봇 자세도 TOP에서 추정한다. 로봇 외관은 바꾸지 않는다. 노랑 롤러·검은 몸체 blob의 배치와 자기 명령 이력(주행 적분)을 결합하는 필터를 먼저 dev에서 잰다. 정답 자세는 평가에만 쓴다.
3. 근거리(≤1.2 m) 최종 접근은 `own_zone_v2`의 근거리 적합(중앙 1.6 cm)으로 TOP 추정을 바꿔 쓴다. 원거리 `far_coarse`는 방향 단서로만 쓴다.
4. 같은 `render/score` 틀에 로봇 자세·ID 정답을 더해 평가한다. 사례는 들린 상자, 이동 중 프레임, 같은 색 인접을 추가한다. dev/test 분할은 이번처럼 먼저 고정한다.
