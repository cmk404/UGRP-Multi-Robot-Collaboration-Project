# 2026-09-24 실시간 명령 끊김과 빔 미세 정렬 시간 (오프라인 분석)

## 질문

같은 빔 미세 정렬이 동기 실행에서는 약 26–28 SIM초 걸리는데 실시간(`--realtime-control`) 실행에서는 35–99 SIM초 걸린다. 원인은 판단 지연 자체인가, 아니면 다른 기제인가?

## 범위

- 기존 로컬 실행 기록만 읽었다(`pair-decisions.json`, `issued-commands.json`). 새 시뮬레이션·모델 호출·학습은 없다.
- SIM 시간과 영상 오차는 제어기가 이미 기록한 값을 사후에 집계한 것이다. 제어 입력에 정답 좌표를 쓰지 않았다.
- 입력 파일 해시는 `survey.json`의 행마다 남겼다. 원본은 기본 체크아웃의 `outputs/` 아래에 로컬로만 있다(원격 백업 아님).
- 대조 A/B가 아닌 **관찰 연구**다. 실시간 실행 39개는 소스 버전(v12–v29, ACT 비교), 지도·자세, 기기 부하가 서로 다르다.
- 동기 실행 90개에는 `retired-worktrees` 아래의 같은 실행 사본이 많다. 독립 표본 수로 해석하지 않는다.

## 기제

`CameraRobotPort.tick()`은 명령 임대(lease)가 끝났는데 다음 명령이 오지 않으면 `hold()`로 모터 명령을 0으로 만든다. 이때 `masterpi_dynamics_v2`는 이동 감쇠(1.4 N/(m/s)) 대신 정지 감쇠(18 N/(m/s))를 쓴다. 따라서 로봇은 약 0.06초 만에 멈추고 쌓인 속도를 잃는다. 로봇 질량(1.10 kg)과 이동 감쇠로 정해지는 가속 시간 상수는 약 0.8초다. 그래서 짧은 명령을 이어서 주면 속도가 누적돼야 제대로 이동한다.

- **동기 실행:** 물리가 판단을 기다리므로 0.2초 명령이 빈틈 없이 이어진다. 이동→이동 전환에서 끊김은 0번이다.
- **실시간 실행:** 판단 주기(v19 두 실행과 2026-09-24 v1 A1: 중앙값 0.24–0.26 SIM초, 90백분위 0.45–0.51초)가 0.25초 임대와 거의 같다. 그래서 이동→이동 전환의 12–86%에서 다음 명령이 임대 만료 뒤에 도착한다. 끊김은 대부분 0.05초 정도로 짧다. 그래도 매번 정지 감쇠가 걸려 다음 명령은 정지 상태에서 다시 가속한다.

## 결과

`analyze.py` → `survey.json`

| 모드 | 실행 수 | 미세 정렬 SIM초 (중앙값, 범위) | r3 이동 전환 중 끊김 비율 | 전진 영상 오차 감소 / 명령 합 (중앙값) |
|---|---:|---|---|---:|
| 동기 | 90 (사본 포함) | 25.8 (24.9–28.4) | 0 | 0.213 |
| 실시간 | 39 | 52.8 (35.2–98.9) | 0.12–0.86 | 0.136 |

- 실시간 39개에서 끊김 비율과 "명령 1단위당 오차 감소"의 순위 상관은 **-0.88**이고, 끊김 비율과 미세 정렬 SIM 시간의 순위 상관은 **+0.79**다.
- 선형 적합은 `미세 정렬 SIM ≈ 34.0 + 54.2 × 끊김 비율`이다. 끊김이 0이면 약 34초로, 동기 26–28초 + 0.25초 임대로 설명되는 수준이다. 이 값은 관찰 기록에서 외삽한 **추정치**이고 측정값이 아니다.
- 명령당 이동이 줄면 같은 거리를 가는 데 이동 명령이 1.5–1.8배 필요하다. 예를 들어 v19 전진 단계는 86–95회, 동기는 54–57회다. 모든 실행에서 부호가 뒤집힌 명령은 0번이었다. 즉 **목표를 지나쳐서 되돌아오는 진동이 아니라, 한 번에 덜 가는 문제**다.

`wheel_model.py` → `wheel-model.json`: 같은 동역학 상수로 만든 1차원 모델에서 명령 1단위당 이동거리(20회 연속)는 다음과 같다. 접촉·요(yaw)·측면 결합은 무시했으므로 절댓값보다 조건 간 비율을 본다.

| 명령 패턴 | 1회 | 5회 | 20회 |
|---|---:|---:|---:|
| 동기 0.20초 연속 | 0.041 | 0.133 | 0.252 |
| 실시간 0.25초 끊김 없음 | 0.059 | 0.193 | 0.330 |
| 실시간 0.25초 + 0.05초 끊김 | 0.059 | 0.111 | 0.128 |
| 실시간 0.25초 + 0.175초 끊김 | 0.059 | 0.069 | 0.071 |

## 해석과 다음 후보 (미검증)

- 실시간 미세 정렬이 느린 주원인은 판단을 기다리는 시간 자체(끊김 합 0.4–17 SIM초)보다, **끊길 때마다 정지 감쇠로 속도를 잃는 것**으로 보인다. 그 결과 이동 명령 수가 늘어난다.
- **후보: 먼 구간 연속 임대.** 먼 구간에서는 다음 판단이 올 때까지 같은 명령의 임대를 이어서 정지 감쇠를 피하고, 목표 근처에서는 지금처럼 정확히 0 명령과 정지 확인을 쓴다.
  - 현재 코드에도 비슷한 장치(`FINE_APPROACH_BRIDGE_EXTENSION_S = .05`, 1회)가 있지만 꼬리 지연을 덮지 못한다.
  - 경계 조건은 다음과 같다. 연장 상한은 RGB TTL 0.6초 이내, 지나칠 위험을 예상 이동량으로 제한, 목표 근처는 제외.
  - 2026-09-24 스케줄 실험(`2026-09-24-fine-gain-schedule`)에서 목표 근처의 작은 0이 아닌 명령이 여러 구간 동안 미끄러져 목표를 지나친 사실을 반영해야 한다.
- 상자 로봇(r2) 단독 이동에서도 끊김(v19: 전환 292회 중 91회)이 있어서, 같은 기제가 상자 접근에도 작용할 수 있다. Codex #131 rolling 작업과 겹치는 영역이다.
- 이 분석은 속도 개선이나 성공을 주장하지 않는다. 후보는 구현·단위 검증 뒤 물리 A/B로 따로 판정해야 한다.

## 재현

```bash
.venv-sim/bin/python experiments/2026-09-24-realtime-stop-gap/wheel_model.py
.venv-sim/bin/python experiments/2026-09-24-realtime-stop-gap/analyze.py
```

`analyze.py`는 기본 체크아웃의 `outputs/**/pair-decisions.json`을 모두 읽는다. 이후 새 실행이 추가되면 행 수가 달라지므로, 이 기록의 기준은 커밋된 `survey.json`이다.
