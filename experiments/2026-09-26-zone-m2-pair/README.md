# 2026-09-26 M2: 실행 중 GT 없는 2인 long_beam 운반

브랜치 `claude/zone-m2-pair`, PR #203(draft). workflow `zone-m2-pair` → `scripts/run_m2_pair.py`. 문서: [docs/zone_m2_pair.md](../../docs/zone_m2_pair.md).

## 질문

두 로봇이 **자기 손목 RGB, 정적 태그 지도, 개략 주문서, 자기 발행 명령**만으로 빔까지 접근하고, 정렬·파지·들기·운반·내려놓기까지 끝낼 수 있는가? pair study(#200)의 `stub_approach`는 사전 정류장까지 GT stub를 썼고, `own_only`는 0.2–0.48 m 뒤에서 출발했다. M2는 두 로봇을 창고 출발점(지도 spawn)에서 출발시키고 실행 중 GT를 전혀 쓰지 않는다.

## 입력 경계

- 로봇 입력은 다음뿐이다. 이 목록은 결과의 `controller_inputs`와 같다.
  - 자기 `robot_cam` JPEG와 자기 발행 명령
  - 정적 태그 지도 `zone_wide_door_tags_v2`와 loop-v2 위치 추정 보정(#201 e10f88d, 읽기 전용 복사)
  - 개략 주문서
    - 빔 설정 자세를 **0.10 m / 10° 격자로 반올림**한 값. 설정 자세 자체는 주지 않는다.
    - 역할, 운반 구간, 속도(pair study 과업표)
  - 승인된 `PairCarrySync` 장벽(자기 frame id)
  - (플래그) 후보 상태 채널. 사용자 결정 대기 중이며 ON과 OFF를 따로 보고한다.
- 정적 keep-out은 두 가지다. 주문서 빔 발자국에 격자 오차 패드 0.06 m를 더한 것, 그리고 상대의 주문서 정류장·사전 정류장(과업표에서 나오는 정적 정보)이다.
- 평가 전용 파일에만 적는 것:
  - 로봇·빔 자세, 위치 추정 오차(`localizer-eval.jsonl`)
  - 손가락 힘, 접촉
  - 실패 전파 지표
- 러너의 `--on-failure continue`(M2 기본)는 상대를 멈추지 않는다. pair study의 "첫 실패에 둘 다 정지"는 러너만 아는 정보여서 `halt_all` 비교용으로만 둔다.
- weld OFF. `cargo_noslip_v1`이 주 프로필이며 사용자 결정을 기다린다.

- **관문**(팔별로 판정하고 따로 보고):

  - **M2-S4 입력:** 모든 결과가 `gt_at_runtime: false`이고 `dirty_source: false`일 것. 경계 테스트(`tests/test_pair_owncam_approach.py`)가 통과할 것.

## 3단계 사전 등록: 실패 전파 (ON/OFF, 동결 전 작성)

- **질문:** 한 로봇이 운반 중 실패했을 때 상대 로봇이 자기 입력만으로 어떻게 반응하는가? 러너는 상대를 멈추지 않는다(`--on-failure continue`). pair study v3는 첫 실패에 러너가 둘 다 멈춰서 이 차이를 잴 수 없었다.
- **seed:** 721–724. `gen_stage3_seeds.py`(rng 20260927)로 만들었고, 뽑는 범위와 거르는 조건은 1단계와 같다. 목록은 `stage3_test_scenarios.json`에 있다.
- **실험자 개입:** seed마다 한 로봇의 집게를 연다. 로봇 명령이 아니며 평가 전용으로 기록한다.
  - 721 r1 3.0 s, 722 r2 3.0 s, 723 r1 6.0 s, 724 r2 6.0 s(운반 시작 뒤 시간)
- **팔:** ON 4회 + OFF 4회. hold check `fullframe_v3`, `cargo_noslip_v1`, weld OFF.
- **측정:** 모두 평가 전용 `failure_propagation`에 남긴다.
  - 첫 실패 로봇·이유·시각
  - 상대의 종료 상태·실패 이유·첫 실패 뒤 종료까지 지연
  - 상대가 첫 실패 뒤 낸 바퀴 명령 수, 마지막 바퀴 명령 시각
  - 실패 뒤 빔 최대 기울기, 최종 빔 높이
- **가설 판정:**
  - **M2-P1:** 피해 로봇이 자기 영상으로 낙하를 감지(`LOAD_CHANGED_IN_CARRY`)한다. 8/8, 개입부터 감지까지 ≤ 1.5 s.
  - **M2-P2(ON):** 상대가 `PARTNER_ABORT`로 멈춘다. 4/4, 첫 실패 뒤 ≤ 0.5 s, 그 뒤 바퀴 명령 0.
  - **M2-P3(OFF):** 상대는 실패를 알 수단이 장벽 제한 시간뿐이다. 그래서 4회 중 ≥ 3회에서 첫 실패 뒤에도 바퀴 명령을 낼 것으로 예상하고, 그 양과 종료 방식을 보고한다.
- **해석:**
  - ON/OFF 차이는 **실패 뒤 상대 행동의 차이**로만 보고한다. 채널 채택 여부는 사용자 결정이다.
  - 낙하 전에 실패한 실행(개입 미적용)은 "측정 불가"로 기록하며 대체하지 않는다.
- **중단 규칙:** 코호트 중 소스 변경 없음. 예외로 끝난 실행은 기록하며, 재실행은 t=0 이전 인프라 오류일 때만 한다.
- **dev 확인(dev3-701-drop, 사전 등록 전, 작업본):** r1의 집게를 운반 3 s 뒤에 열었고, 0.9 s 뒤 r1이 `LOAD_CHANGED_IN_CARRY`로 감지했다.
  - ON: r2가 같은 제어 tick에 `PARTNER_ABORT`로 멈췄고, 그 뒤 바퀴 명령은 0이었다.
  - OFF: r2가 16.5 s 동안 바퀴 명령 160개로 운반을 계속했다. 빔 기울기는 최대 6.1°였고, 36.7 s 뒤 `BARRIER_LOWER_TIMEOUT`으로 끝났다.
  - dev 뒤 수정은 평가 전용 한 가지다. 루프 종료 시 마지막 정답 표본을 1개 추가했다(ON에서 실패 뒤 빔 기울기가 비어 있었다).
- **소스:** 동결 커밋(아래 결과에 적음)의 `open_floor` 경로는 1단계 동결본(3fdf011)과 같은 동작이다. 추가된 문 단계 코드는 `--stage door`에서만 실행된다.
