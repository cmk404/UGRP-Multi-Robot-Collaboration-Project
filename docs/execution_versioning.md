# 실행 버전 관리

실험의 버전은 코드 SHA와 실행 조건을 함께 식별한다. 같은 스킬 코드를 호출해도 물리 설정이나 명령을 적용하는 방식이 다르면 다른 실행이다.

2026-09-23 단독 운반 비교에서는 기존 성공 경로의 `local_contact_fine` 설정이 공통 실행기에 전달되지 않았고, `VisualMacroExecutor`와 `MacroQueue`의 이동 궤적·안정화 시간도 달랐다. 영상 크기 수정과 단위 검사 통과만으로 성공 경로 복원을 확인할 수 없었다. 이 문서의 절차는 이런 차이를 실행 전에 드러내고 과거 성공 판정의 잘못된 승계를 막는다.

## 함께 고정하는 정보

| 범위 | 기록·검사 대상 |
|---|---|
| 코드 | 실행 SHA, 작업 트리 변경 여부, 주요 실행 소스의 해시 |
| 물리 | 접촉 프로필, 실제 timestep, 명시 접촉쌍, weld 사용 여부 |
| 입력 | 카메라·지도 식별값, RGB 크기·인코딩·전처리 |
| 명령 | 실행기, 보간 방식, 이동 시간·안정화 대기, 관측·명령 적용 주기 |
| 자산·환경 | 실제 모델/참조 영상/지도 해시, Python·관련 패키지·플랫폼 버전 |
| 근거 | 검증한 조건·실행 SHA·결과 위치와 해시, 성공/실패/미검증 구분 |

접촉 설정은 시뮬레이터의 물리 계산 조건이며 로봇에게 제공할 접촉 관측이 아니다. 실행 번들 검사는 제어 입력에 정답 정보나 평가값을 추가하지 않는다. 시뮬레이션 성공은 실물 접촉 보정을 입증하지 않는다.

## 변경과 검증 순서

1. 재사용할 성공 실행과 실행 번들을 먼저 고른다. 원본 코드·설정·성공 근거가 없는 실행을 성공 기준으로 새로 등록하지 않는다.
2. 실행기를 옮기거나 설정을 바꾸면 기존 번들을 덮어쓰지 않고 새 버전으로 등록한다. 성공 기준과 달라진 항목을 기록한다. 새 버전의 검증 상태는 미검증에서 시작한다.
3. 실행 전 검사로 누락된 선택, 소스·설정 불일치, 지원하지 않는 조합을 확인한다. 실패를 기본값 대입이나 검증 우회로 통과시키지 않는다.
4. 최종 코드를 커밋하고 코호트 동안 고정한다. 각 실행에 번들 ID·해시와 실제 적용값, 자산·환경·코드 식별값을 저장한다. 같은 ID라도 해시나 환경이 다르면 동일 조건이라고 단정하지 않는다.
5. 관련 자동 검사 후 동일 조건의 실제 단독·공동 실행을 검증한다. 성공·실패 모두 새 실험 ID에 보존하고 원본은 유지한다. 완주 검증 전에는 기존 성공률을 새 버전에 붙이지 않는다.

자동 검사는 설정 누락과 알려진 실행 계약의 변경을 검출한다. 물리적 완주나 일반화 성능을 대신 검증하지 않는다. 적용된 실행 경로 밖의 도구는 별도 검토가 필요하다.

## 공통 RGB 실행기에 적용된 검사

`config/rgb_execution_bundles/`에 버전별 JSON을 보존한다.

- `dispatch-f1-local-contact-fine-v1`: 기존 `e099a4a` F1 성공의 참조 기록이다. 원래 실행기·접촉 설정과 원본 결과 해시에만 성공 근거가 적용되며 공통 adapter에서 선택하면 거절한다.
- `rgb-adapter-legacy-v1`: PR #113 당시 공통 adapter 조건을 보존한 실험 버전이다. 기존 JSON과 소스 해시는 변경하지 않는다. 현재 코드로 실행할 수 없으며 당시 checkout에서 재현한다.
- `rgb-standard-dispatch-v2`: 표준 장면 생성·초기화와 연결한 2026-09-23 이전 후보다. 당시 소스와 실행 조건을 보존한다.
- `rgb-standard-dispatch-v3`: beam 접근 중 양쪽의 새 TOP RGB로 전진 간격을 제한하는 현재 후보이다. `legacy` 접촉 설정과 adapter의 명령 일정은 유지한다. 16px 제한은 새 제어 정책 설정이며 실제 접근·운반 완주 결과로 아직 검증되지 않았다. 과거 성공 프로필 `local_contact_fine`과도 별도 조건이다.

새 backend 설정 schema는 `ugrp.rgb_skill_backend.v2`다. `execution_bundle_id`가 없거나 지원하지 않는 조합이면 거절한다. 과거 v1 설정은 당시 실행 기록으로 보존한다. 실행 전 정적 검사는 다음과 같다. 시뮬레이션·렌더링·외부 모델 호출은 하지 않는다.

```sh
python3 -m harness.rgb_execution_bundle verify-current --id rgb-standard-dispatch-v3
python3 -m harness.rgb_execution_bundle verify-registry --base origin/main
```

첫 명령은 등록된 버전과 현재 핵심 소스의 일치를 검사한다. 둘째 명령은 기준 Git ref에 이미 존재하는 번들의 변경·삭제를 검사한다. 기준 ref를 읽지 못하면 먼저 저장소·원격을 확인하고 정상적으로 fetch한 후 다시 검사한다.

실제 backend를 만들 때는 적용된 장면·물리 모델·카메라 설정과 명령 일정을 다시 확인한다. 정적 검사 통과만으로 이 단계를 통과했다고 보고하지 않는다. 결과에는 번들 ID·해시, 실제 적용값, 성공 기준과의 차이 및 자산·환경·코드 식별값을 남긴다. 이 정보는 감독·평가 기록이며 actor의 추가 관측으로 전달하지 않는다.

기존 버전의 소스나 조건을 변경하려면 새 ID의 manifest와 해당 버전을 지원하는 코드를 함께 PR로 제출하고 회귀 검사를 수행한다. 성공 여부는 새 실험 기록에서 정확한 번들 해시에 연결한다. 과거 실험 설정을 새 필수 필드에 맞추려고 소급 수정하지 않는다. 과거 재현에는 그 당시 Git SHA의 실행 경로와 원본 자산을 사용한다.
