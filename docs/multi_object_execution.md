# 다중 물건 RGB 식별과 단계 실행 파일럿

12조건 장면에 RGB 식별과 작업별 실행 어댑터를 연결했다. **봉 1개·상자 2개의 실제 5작업 완료는 아직 실패**다.
현재 실행기는 실험용 Gemini raw-action 정책이며 기존 학습 파지 정책이나 ACT를 연결한 것으로 표현하지 않는다.
[전체 실행 기록](../experiments/2026-09-20-multi-object-rgb-execution/README.md)을 참고한다.

## 입력과 식별

- 학생에게 자기 RGB, 고정 공용 TOP, 자기 발행 명령, 작성된 정적 과제/지도, 수신한 동료 주장을 제공한다.
- TOP의 기존 청록 상자/주황 봉을 색·형상으로 검출한다. 외관·라벨·카메라/FOV는 바꾸지 않는다.
- 동종 물건의 ID는 최초 TOP에서 **왼쪽 열부터, 같은 열 안에서는 아래부터 위로** 붙인다.
  이는 영상에서 정의한 임무 이름 규칙이며, 물리 body/geom ID나 시작 좌표 조회가 아니다.
  열 분리 기준은 영상 폭의 0.025이며 이 개방 맵 파일럿의 명시적 관례다.
- 이후 ID는 재정렬하지 않는다. 시간·이동량·면적에 따른 일대일 연결이 유일할 때만 갱신한다.
  검출 수 불일치는 정지, 짧은 가림은 제한된 이동 범위 안에서 재관측, 복수 연결 가능성이나
  0.8초 이상의 식별 공백은 새로운 임무 식별이 필요하다고 보고 정지를 유지한다.
- 정답 위치/마스크는 제어에 전달하지 않는다. 자세를 바꿔 렌더링하는 별도 추적 진단에서는
  영상 판정 **후에만** 정답과 비교한다. 이 진단은 물리 운반이나 교사 파지 성공이 아니다.

## 실행 연결

`MultiObjectExecution`은 세 로봇의 동일 계획 ACK 후 `MissionProtocol`의 작업·물건·로봇·목적지·경로
예약을 가져온다. 각 로봇은 독립적인 TOP 추적 상태와 자기 명령 이력을 가진다.
`lane_a/lane_b`는 이 개방 맵의 논리 예약이며, 안전한 주행 경로를 보증하지 않는다.

APPROACH는 현재 식별과 작업 예약이 있는 로봇만 0.2초 명령을 발행한다. 영상에서 파지 자세와
정지를 확인했다는 새 보고가 있어야 이후 단계에 진입한다. GRASP → LIFT → CARRY → LOWER → RELEASE는
모두 `TaskStageExecution` / `TaskStageSync`를 거친다. 단독 상자는 명시적인 `solo` 역할에 한해
한 참여자로 같은 계약을 사용하며, 기존 `PairCarrySync` 기본 두 참여자 요건은 유지한다.

작업 허가는 단계 허가를 대신하지 않는다. 완료는 해당 단계에서 발행된 명령과 그 이후 새 영상에
묶인 참가자 전원의 주장이어야 한다. 식별 손실·계획 취소·누락/과거 응답·만료는 동작을 멈추고
예약을 보존한다. 다음 작업은 필요한 선행 작업이 끝나야 열리며, 임시 적치 슬롯 점유도 유지한다.
명령·요청·작업 사건에 task_id/object_id/plan_version을 기록한다. 단계 내부의 기존 보고는 해당
TaskPlan에 묶여 있다. 물리 성공은 별도 평가이며, 모델의 DONE이나 명령 발행으로 올리지 않는다.

실행 중 동료 메시지는 검증된 텍스트 주장만 전달한다. 상대 자기 영상/비공개 명령 이력을 합치지 않는다.
최신 메시지 전달 패치는 단위 테스트로 검증했으며 아래 v1–v3 모델 코호트 이후에 추가됐다.

## 재현

실행 전 소스를 커밋하고 로컬 프록시의 `/v1/models`에서 실제 모델을 확인한다.
다음 명령은 모델 호출을 발생시키며 새 출력 폴더를 사용한다. API 청구 금액은 현재 프록시에서 제공하지 않는다.

```sh
.venv-sim-worker-mac/bin/python scripts/ugrp_session.py run multi-object-NEW -- \
  .venv-sim-worker-mac/bin/mjpython scripts/run_multi_object_execution.py \
  --case staging_three --model gemini-3.8-flash --output outputs/multi-object-NEW \
  --turns 10 --max-calls 24 --max-input-tokens 220000 --max-wall-s 240
```

호출 중 SIM은 멈춘다. 입력 토큰 예산은 누적 사용량과 다음 호출 예약량으로 판단하며, 제공자가
사후 사용량을 반환하므로 엄밀한 토큰 상한을 보장하는 API 기능은 아니다. 호출 수 상한은 별도다.
평가의 최종 위치는 운반 과정의 들어올림·임시 적치·선행 순서를 입증하지 않는다.
현재 결과는 0/5 완료, 최종 목적지 0/3이며 파지 단계에 진입하지 못했다.

## 확인한 범위와 남은 일

- 저장된 12조건 초기 RGB에서 물건 개수·초기 ID 바인딩 확인.
- 별도 렌더링 자세 변화 16프레임 × 물건 3개에서 잘못된 ID 연결 0개.
- 합성 영상 판정을 사용하는 실제 포트 계약 테스트에서 5작업 전환/예약/정지/오래된 보고 차단 확인.
- 실제 Gemini 계획 합의와 동시 접근 명령을 확인했으나, 반복 파지·운반·완료는 미달.

다음 병목은 목표 ID를 유지하는 기존 RGB 접근·파지 정책 연결이다. raw LLM의 짧은 바퀴 명령을
반복 호출하는 방식으로는 이번 예산 안에 기본 접근도 끝나지 않았다. 먼저 단일 상자의 접근·파지를
닫힌 루프로 검증한 뒤 동일 로봇 재사용, 봉 협동, 5작업, 4–8개 확장을 순서대로 검증한다.
ACT의 일반 경로/목표/반복 작업 입력 계약 및 재학습, 물건을 실제로 운반하며 발생하는 가림·교차·회전,
교착 복구와 임무 중 ID 재확정은 후속이다. 이번 파일럿을 배포용 운반 정책으로 채택하지 않는다.
