# 로컬 MuJoCo 실시간 실행 검증

물리 owner가 RGB 렌더·판단·관찰 창 때문에 멈추는 문제를 분리한다. `protocol.json`의 동일 open/seed11 계획·모델·카메라·접촉 설정을 고정한다. 실제 timestep은 0.00025초, weld는 OFF, 새 LLM 호출과 학습은 0회다. 각 물리 실행 전 코드를 커밋하며 원본을 덮어쓰지 않는다.

첫 계측과 실패 실행의 해시·소스·입력·영상·TensorBoard 검증은 `initial-diagnostics.json`에 있다. 180초 cProfile 진단은 기한 중단이며 완주 시간 비교에 포함하지 않는다. v8(`f2d6ced`)은 95.803초 뒤 공동 운반에서 중단됐다. 5개 판단 모두 실제 RGB 촬영 시각보다 0.70–0.74 SIM초 늦어 0.6초 제한을 넘었고, 운반 명령은 양쪽 HOLD였다. 낮은 종료 시간을 속도 개선으로 해석하지 않는다.

원본은 기본 checkout의 `outputs/simulation-realtime-20260923/{profile-baseline,native-v8}`에 보존한다. 기존 TensorBoard 서버의 `0923-실시간-진단/{계측,v8}`에 두 실패를 별도 등록했으며 이벤트 값 로딩과 MP4 Range 206 응답을 검증했다. 새 후보는 접근·파지의 비동기 관측, 동일 JPEG 분할 재사용, 지연 원인 분리 및 독립 관찰 창의 Mac launcher를 통합한다. 완주 결과는 별도 결과 기록으로 추가한다.

v9(`5f14753`)의 native 실행에서는 motion 구간 56.480 SIM초/56.482 wall초(1.000×)를 기록했다. 모든 pair 영상은 0.6초 제한 이내였지만 초기 접근 120회 한도를 소진했고 화물은 이동하지 않았다. `independent-audit-v9.json`과 `v9-pair-stage-latency-audit.json`에 원본 해시 및 수치를 기록한다. 0.2초 명령마다 관측 중 중앙값 0.26초의 명령 공백이 있었다. v10은 다음 RGB 처리를 이동 명령과 겹치고 정지 확인의 전체 dwell을 유지하는 후보다. 기존 성공 v7과의 완주 시간 비교는 성공 재실행이 생긴 뒤에만 계산한다.

단위 검사·동일 픽셀/분할 후보 검사는 실제 운반 성공을 의미하지 않는다. headless·native·녹화와 공동 운반·ACT·새 지도 성공을 각각 구분한다.

v10(`25a88b8`)은 motion 28.980 SIM초/28.984 wall초(1.000×), 36.962 wall초에 접근 120회 한도를 소진했다. pair RGB age 중앙값 0.20초·최대 0.40초로 신선했지만 명령 주기 중앙값 0.22초에 0.20초 lease가 끝나 반복 정지가 남았다. 양측 120회 동일 시각 발행이며 각 로봇 명령 공백 합계 4.86 SIM초였다. v11은 초기 접근 이동 lease만 0.25초로 조정하는 단일 변수 진단이다. 모델·판단 임계값·120회 한도·0.6초 영상 TTL·정지 확인 dwell은 유지한다.

v11(`ea9759e`)은 coarse 71회 및 정밀 yaw/lateral/yaw를 통과했으나 정밀 forward 단계의 이동 160회 한도를 소진했다. 모델 입력 유효성 이탈이 아니라 이동 예산 실패다. wall107.137초, motion98.310 SIM초/98.821 wall초; 물리·프로토콜 성공 false. v12는 open realtime 정밀 접근의 이동에도 같은 최대0.25초 갱신을 적용한다. 물리 감쇠와 성공/지원 임계값은 변경하지 않는다. `v10-drive-kernel-trajectory-audit.json`의 단일 로봇 무하중 진단은 동일 명령 trace에서 kernel/legacy의 모든 timestep 상태 차이0과 정지 공백의 감쇠 효과를 구분해 기록한다.

v12(`6fd23ae`)는 coarse88회, 정밀 7단계의 정지 확인, 파지를 모두 통과하고 계획된 운반 10회 한도에서 중단됐다. wall109.115초, motion100.220 SIM초/100.232 wall초. 운반 영상 age0.44–0.64초, 유효9/오래된영상HOLD1이며 물리·프로토콜 성공은 false다. 운반 첫 프레임의 빔 특징 계산과 명령 갱신 공백을 추가로 검토해 `protocol.json`에 유한한 후속 진단 예산을 기록했다. 완료하지 않은 진단 시간을 완주 속도 비교로 사용하지 않는다.

v13의 첫 프레임 빔 특징 계산은 단면별 반복 배열 탐색을 그룹 정렬로 바꾸고, contour의 경계 상자 안에서 마스크를 만든 뒤 원래 픽셀 좌표를 복원한다. v12 저장 TOP 11장의 18개 포화도 조건별 전체 후보는 기존 결과와 정확히 일치했다. 첫 계산 중앙값은 약0.147→0.044 wall초였다. 이 CPU 재생 수치를 전체 시뮬레이션 속도로 해석하지 않으며, 운반 갱신과 결합한 실제 진단을 별도로 수행한다.


v13(`d4b2059`) 진단은 운반 40회 제한까지 진행했고 motion105.140 SIM초/105.402 wall초, stale0이었다. 같은 소스 전체 실행은 운반167회 뒤 현재 RGB의 고포화 중심선 합의 부족으로 중단됐다. wall167.796초, 빔 이동0.548m, box이동0.109m, 물리·프로토콜 성공 false이며 완주 시간 비교에서 제외한다. `independent-audit-v13*.json`에 해시와 TensorBoard 실패 등록을 보존한다.

v14는 기존 고포화 판정이 실패할 때만 현재 저포화 RGB의 동일 중심선 합의와 고포화 fit의 교차 확인을 요구한다. 원본 v13/v7 유효판정277개는 그대로이고 실패9개가 재생에서 회복됐으나 새 조건 성공률은 아니다. Solo 작업자의 권한 요청은 사본에서 계산하고 owner가 최신 결과의 권한을 재검증해 확정하며, 직접 carry/yield 이동은 최대0.25초 명령과 다음 관측을 겹친다. 원본영상+0.6초 만료와 zero/HOLD·pose 간격은 보존한다. 추가 유한 검증 예산은 protocol에 기록하며 실제 완주는 별도 확인한다.
