## 출처 구분

- **1차 진단은 Codex**(gpt-6-astra, xhigh, 읽기 전용 분석)가 했다. 슬롯 `r3` = 물리 `r1`, H2(분포 이동) 판정, 관절·베이스·바퀴 비교, 연결 검사 수치를 냈다.
- Codex는 sandbox 제한으로 기록·커밋·코멘트를 남기지 못했다. 이 문서의 수치는 전부 [analyze_r3_pose.py](analyze_r3_pose.py)로 **독립적으로 다시 계산**했다. Codex 수치를 근거로 합산하지 않았다.
- 반사실 렌더와 특징 분해(아래 3–4절)는 이번에 새로 한 분석이다.

## 1. 슬롯 → 물리 로봇 대응: `r3` = 물리 `r1` (확인)

다섯 가지 근거가 모두 `{슬롯 r1: 물리 r3, 슬롯 r3: 물리 r1}`로 일치한다(Y1·Y2 동일).

| 근거 | 결과 |
|---|---|
| 코드 규칙: `harness/dispatch_skill_binding.py` `SkillBindings`의 `upper, lower = participants`, `pair = {'r1': lower, 'r3': upper}` | 계획의 beam 참가자 순서 `[r1, r3]` → 슬롯 r3 = r1 |
| `skill-bindings.json` `pair_model_slots` | `{r1: r3, r3: r1}` |
| `pair-decisions.json`: image_binding 436개의 `pair_binding`, coarse receipt 138개의 `physical_robot_id` | 모두 같은 값 |
| 미세 정렬 호출 488개의 자기 RGB 파일명 | 슬롯 r3 → `…-r1.jpg`, 슬롯 r1 → `…-r3.jpg` |
| TOP 투영(평가 전용): 첫 거친 판정 시각의 물리 베이스 위치를 `cctv_top`에 투영 | 물리 r1 (117.5, 149.8) px ↔ 슬롯 r3 바퀴 중심 (115.4, 145.3) px |

따라서 이전 기록에서 실패 로봇 "r3"는 **모델 슬롯 r3 = 물리 r1**이다. 실행 기록 전체가 모델 슬롯 이름을 쓰므로, 슬롯 r1(물리 r3)의 수치도 마찬가지로 읽어야 한다.

## 3. 반사실 렌더: 무엇이 잔차를 되돌리나

**렌더 충실도.** 수정하지 않은 qpos로 렌더하면 기록된 원본 TOP과 맞는다.
- 재접근 1·2: 픽셀 차이 0, 잔차 12.11·12.51이 정확히 재현된다.
- 재접근 3: 로봇이 움직이는 중이고 replay 프레임이 3.2 ms 앞서서, 평균 0.016·최대 62 차이가 났다. 잔차는 15.26(기록 15.49)이다.

**방법.** F 프레임에서 한 요인만 G 값으로 바꾸고(F+G), 거꾸로 G 프레임에 F 값을 넣었다(G+F). canonical 평행 이동은 기록값 (212, 96)으로 고정했다. F와 G의 기록값이 같다. 한계는 11.56이다.

| 바꾼 요인 | 재접근 1 F+G / G+F | 재접근 2 F+G / G+F | 재접근 3 F+G / G+F |
|---|---|---|---|
| 없음 (F / G) | 12.11 / 5.11 | 12.51 / 5.11 | 15.26 / 4.15 |
| 물리 r1 바퀴 4개 | 11.71 / 5.52 | 12.71 / 5.60 | 14.73 / 5.66 |
| 물리 r1 베이스 위치·자세 | 11.69 / 5.74 | 12.05 / 6.26 | 23.26 / 5.05 |
| 물리 r1 팔·집게 | 12.11 / 5.11 | 12.51 / 5.11 | 15.35 / 4.26 |
| 물리 r1 전체(베이스·바퀴·팔·집게) | 11.56 / 6.50 | 11.56 / 6.15 | 14.40 / 6.35 |
| 다른 로봇 전체 | 12.11 / 5.11 | 12.51 / 5.11 | 15.26 / 4.15 |
| **빔 위치만** | **6.50 / 11.56** | **6.15 / 11.56** | **6.35 / 14.40** |
| 빔 자세(회전)만 | 12.11 / 5.11 | 12.51 / 5.11 | 15.26 / 4.15 |

주석:
- 물리 r1 전체의 F+G 11.56은 한계와 같은 값이라 통과가 아니다(예측 함수는 `residual > limit`일 때 거부).
- 물리 r1 전체를 바꾼 F+G와 빔만 바꾼 G+F는 잔차가 같다(11.56 / 11.56 / 14.40). ROI 안에서 보이는 두 프레임의 차이가 물리 r1과 빔뿐임을 시사한다.

**바퀴 각 스윕.** F 프레임에서 네 바퀴를 함께 0–345°(15° 간격) 돌렸다.
- 재접근 1: 잔차 11.53–12.39. 24개 중 3개가 한계 바로 아래(11.53–11.55)였다.
- 재접근 2: 11.65–12.68. 통과한 각도가 없다.
- 재접근 3: 7.67–15.82. 두 각도(+225°, +255°)만 통과했다.
- 즉 바퀴 외관은 잔차를 흔드는 부차 요인이다. 다만 G의 실제 바퀴 각으로는 세 경우 모두 복구되지 않았다.

**빔 이동량(replay, 평가 전용).**
- 주입된 파지 실패로 빔이 7.8 cm 들렸다가 내려왔다.
- 내려온 뒤 처음 위치보다 x −0.59 mm, y −0.14 mm, yaw −0.021° 어긋나 그대로 머물렀다(t≈65.9 s 이후 불변).
- TOP 해상도(빔 0.45 m ≈ 123 px)로 약 0.16 px이다. 정수 픽셀 평행 이동으로는 보정할 수 없는 크기다.

## 4. 기전: 학습 배경에 들어간 빔 가장자리

- 기하 모델은 학습 TOP들의 중앙값을 배경으로 쓰고, 그와 18 이상 다른 픽셀을 전경으로 본다(`harness/camera_varied_start_geometry.py`).
- 교사 시연에서는 빔이 항상 같은 자리에 있었다. 그래서 **빔이 배경에 들어 있다.** 첫 접근에서는 빔이 전경으로 잡히지 않는다.
- 빔이 0.16 px 밀리면, 슬롯 r3 ROI 안의 빔 북쪽 끝 가장자리가 배경과 달라진다.
  - 폭 수 px의 전경 조각이 생기고, 그 조각은 노란색이다([그림](figure-r3-roi-masks.jpg)의 가운데 열, 빔 끝의 빨간 띠).
  - lateral 실패: ROI (0.72, 0.73)에 26–27 px의 새 노란 연결 성분이 생긴다. 이 때문에 `yellow_x2`, `yellow_xy`, `yellow_comp5_*` 특징이 학습 분포를 크게 벗어나며, 잔차 성분은 +5.7, +3.8, +4.3 등이다.
  - forward 실패: 55 px 전경 성분 `fg_comp2_*`(+10.2)가 추가된다.
- 빔만 G 위치로 돌리면 이 성분들이 사라지고 잔차가 6.15–6.50으로 내려간다.
- **같은 원인이 v60 기록의 hue≤24 축 변화도 설명한다.** F 원본 렌더의 hue≤24 빔 축은 95 px(중심 y 277.5)이다. 빔만 처음 위치로 돌리면 123 px(중심 y 263.5)가 된다. hue≤35는 두 경우 모두 127 px(중심 y 261.5)로 같다.

**판정: H2(분포 이동) 확인. 직접 원인은 재파지 실패 뒤 빔의 0.59 mm 정지 위치 변화이며, 로봇 자세·위치·바퀴가 아니다.**
- 학습 배경에 고정된 빔 가장자리가 새 노란·전경 성분으로 바뀌어 직교 잔차를 한계 밖으로 밀었다.
- 로봇 위치(0.8–7.5 mm)와 바퀴 각(27–130°)은 잔차를 조금씩 움직이는 부차 요인이다. 단독으로는 세 실패를 설명하지 못한다.

참고: 첫 접근에서도 forward 단계 frame 166에서 슬롯 r3 잔차 17.48로 한 번 지원 밖이 나왔다. 재관측 뒤 통과했다. 이때 빔은 처음 위치였으므로 이번 원인과 다르며, 따로 분석하지 않았다.

## 검증 범위와 한계

- **재현성:** Y1과 Y2의 replay·결정이 같아서 두 실행은 사실상 한 사례다. 비율이나 일반성은 주장하지 않는다.
- **렌더 동일성:** 오프라인 렌더는 같은 Mac·같은 `model.mjb`로 했고, 기록 영상과 픽셀 단위로 맞았다(재접근 1·2). 다른 호스트나 GL에서 픽셀이 같다는 것은 확인하지 않았다.
- **반사실의 범위:** 한 요인씩, 그리고 한 쌍의 F/G 프레임만 바꿨다. 조명·그림자는 따로 조작하지 않았다. 빔 위치를 바꾼 반사실에는 빔 그림자 변화가 함께 들어 있다.
- **조치 효과 미확인:** 이 분석은 원인 분리까지다. 수정은 없다. 모델·코드·지원 한계를 바꾸지 않았고, 새 번들이나 새 모델도 만들지 않았다.
- **TensorBoard:** 새 실험·학습·평가 결과가 아닌 오프라인 진단이라 갱신하지 않았다(작업 지시).

   - 먼저 이 스크립트의 반사실 렌더로 빔을 흔든 영상을 만들어 새 모델을 오프라인으로 확인한다.
   - 그다음 새 실행 번들 ID로 사전 등록한 SIM 실행에서 재파지 복구를 확인한다.
