# 3대 계획 합의 → 공동 운반 최소 구성

**최종 실제 모델 3조건 모두 접근·파지·운반·내려놓기·해제 성공.**
세 로봇이 같은 계획에 승인한 뒤 R1/R3가 운반하고, R2는 목적 구역을 정지 상태에서
관찰한다. 실행 코드 `d79c97d8f03c6ea7a8e067c4e4c06519d4b19b82`를 세 조건에서 고정했다.
이는 지원 기술을 제한한 통합 검증이며 자유로운 운반자 선정이나 통신 효과 실험은 아니다.

## 연결한 행동

1. R1/R2/R3는 각자의 자기 RGB·공용 TOP RGB·자기 발행 이력·받은 메시지로 판단한다.
2. 순환 제안자가 계획을 내고, 세 로봇이 같은 제안 ID·버전·해시에 명시적으로 승인해야 출발한다.
3. R1/R3는 기존 RGB 제어와 시연 팔/RGB 보정 기술로 접근·파지·운반·놓기를 실행한다.
   매 공동 단계에서 두 로봇의 새 영상 허가를 확인한다.
4. R2는 별도 모델 요청으로 목적 구역을 관찰한다. 세 실행 모두 `during_approach`를
   선택했고, R2 추론과 접근 실행 구간의 실제 시간 중첩은 각각 3.37/2.08/3.48초다.
   이는 세 로봇의 동시 물리 이동을 의미하지 않는다.
5. R2의 장애물 보고·보고 실패는 운반 전 정지/재계획 요청으로 연결한다. 과거 CLEAR는
   운반 허가가 아니며 R1/R3가 새 RGB로 판단한다. 자동 우회/재계획 실행은 후속 범위다.

현재 지원하는 운반자는 고정 R1/R3다. 모델 선택은 이 기술의 수락/거절과 R2의 관찰 시점이다.
R2가 다른 물체를 운반하거나 세 대가 같은 물체를 잡는 기능은 없다.
상위 계획/로봇별 실행을 대신하는 범용 제어기보다 동기화 담당의 연결 경계를 구현한 결과다.

## 최종 실제 모델 결과

모두 같은 평지·물체·60/60cm 출발·yaw/lateral 0 조건을 사용했다.

| 조건 | 결과 | 협상 | 주입된 대기 | 실제 시간 | SIM 시간 | 모델 요청 |
|---|---|---|---|---|---|---|
| 정상 | 성공 | 제안+전원 승인 2회 | 없음 | 125.48초 | 48.36초 | 25 |
| 준비 지연 | 성공 | 2회 | LIFT R3 보고 2회 보류, 0.4 SIM초 대기 | 129.56초 | 48.76초 | 29 |
| 운반 보고 단절 | 성공 | 2회 | R3 보고 5회 보류, 1.0 SIM초 양쪽 바퀴 명령 0 | 102.72초 | 50.56초 | 25 |

보고 단절 구간은 운반 12~16회다. 각 회 HOLD와 양쪽 0 명령을 재생 확인했다.
이후 양쪽 새 영상 보고를 받은 뒤 재개했고, 평가에서는 들림·운반 연속성과
내려놓기·해제 후 안정 조건을 모두 통과했다. 실제 네트워크 단절이나 고장 주입은 아니다.
세 실행 목표 오차 절댓값은 1.71/1.71/1.88cm, 접근 중 화물 접촉 0, weld 활성 0이다.
초기/종료 카메라(세 자기 시점 포함)·FOV·형상·마찰·질량 해시가 일치했다.

최종 79개 실제 모델 요청: 입력 379,057토큰, 출력 11,410토큰, 공급자 total 398,935토큰.
공급자 total의 기타 사용량을 별도 해석하지 않는다. 사용량 누락·요청 오류는 0이며
청구 금액은 제공되지 않아 미상이다. 실행 중 다른 로컬 실험도 존재했고, 조건별 1회이며
모델 응답과 지연이 다르므로 실제 시간 차이를 성능 우열로 해석하지 않는다.
운반 로봇의 LLM 단계 판단 중 SIM은 정지한다. R2 관찰만 별도 요청으로 접근과 겹친다.

## 실패와 연결 진단도 보존

- `b388857`, 고정 응답 연결 진단: 운반 성공. LLM 계획·R2 영상 이해 증거로 합산하지 않는다.
- `5c1680b`, 첫 실제 모델: 18회 요청 후 협상 실패. 제안 전 R2/R3의 정상 대기
  (`accept=false, plan=null`)를 잘못 거부해 R1 제안을 등록하지 못했다.
  팔 초기 접기 이외 작업 명령이 없었음을 실제 trace에서 확인했다.
- `d79c97d`, 수정: 제안은 제안자의 응답으로 등록하고, 실행은 이후 세 명의 정확한
  ACK로만 허가하도록 분리했다. null 계획으로 승인하는 응답은 계속 거부한다.
- 같은 최종 소스의 `before_carry` 고정 응답 연결 진단도 운반 성공. 이 대체 순서의
  실제 모델 선택/관찰 성공은 검증하지 않았다.
