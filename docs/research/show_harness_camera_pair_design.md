# Show-Harness 기반 카메라 전용 공동 파지 설계

작성: 2026-09-14. 상태: **구현 전 설계**, 실험 결과 없음.
요청: Show-Harness를 UGRP에 적용하는 구체적인 구조와 검증 계획.
확인한 기준 코드: `main` / `266a4e7` (원격과 일치). 실행 코드 변경·모델 호출·로봇 구동 없음.

## 1. 연구 질문과 범위

RQ1: 같은 VLM과 카메라 관측에서 숫자 명령을 작고 설명 가능한 이산 행동으로 바꾸면 공동 파지가 개선되는가?
RQ2: 자기 발행 명령 기억과 이전 영상은 각각 얼마나 도움이 되며 행동 표현과 상호작용하는가?

첫 과제는 r1/r3가 주황색 빔을 함께 잡아 3 cm 이상 들어 2초 유지하는 것이다. 이동 운반은 이 단계의 결과와 평가기를 검증한 뒤 확장한다. 상대 로봇과의 메시지, 중앙 계획자, 행동 청킹, 온라인 시각 학습, VLM 파인튜닝은 첫 비교에 넣지 않는다.

이 작업의 차별화 후보는 카메라만 사용하는 독립 두 에이전트의 행동 인터페이스와 시간 문맥이다. Show-Harness를 이식했다는 사실만으로 연구 기여나 새로운 방법이라고 주장하지 않는다. 논문 수준의 신규성 판단에는 추가 선행연구 검토가 필요하다.

## 2. 논문에서 가져올 것과 변경할 것

- 가져올 것: 작고 명확한 행동 단위, 행동-재관측 루프, 같은 행동 어휘로 시연 수집과 학생 학습을 연결하는 구조.
- 수정할 것: 원 논문 기본 구성의 높이·접촉·그리퍼 상태 피드백 및 상태 기반 복구를 제거한다. 실패 판단과 재시도 결정도 허용된 영상에 근거해 모델이 수행한다.
- 로봇별 실행기는 필요하지만, 첫 버전은 Cartesian 끝점 이동이나 IK 대신 발행 명령 기준의 관절 펄스 증분을 사용한다. 이를 원 논문의 끝점 의미 행동과 동등하다고 표현하지 않는다.
- 원 논문의 양팔 행동 공동 예측과 달리, 여기서는 두 모델 요청과 기억을 분리한다. 동시 실행 시각을 맞추는 호스트는 행동 내용을 결정하지 않는다.
- 원 논문 §5.4.4의 행동 설명 효과를 참고한다. 첫 비교의 모든 조건에 동일한 하드웨어 설명을 주며, 설명 유무 실험은 후속 비교로 분리한다.

## 4. 데이터와 모듈 경계

```text
fixture owner: 고정 초기 명령·배치, 카메라/FOV, 물리 설정
                         |
                     RGB snapshot
                 /                   \
       r1 자기 RGB + 공용 top    r3 자기 RGB + 공용 top
       r1 전용 문맥 / VLM        r3 전용 문맥 / VLM
                 |                   |
       raw 또는 이산 행동        raw 또는 이산 행동
                 |                   |
       r1 명령 변환기             r3 명령 변환기
                 \                   /
                 CameraRobotPort.apply
                         |
                   고정 1초 물리 실행
                         |
                       다음 RGB

physics -> 평가 전용 JSONL -> 실행 종료 후 평가 / 영상 검토
             (actor·변환기·단계 전환으로 돌아가는 경로 없음)
```

모델에는 작업 설명, 고정 명령 설명, 자기 RGB·공용 top RGB 및 조건별 자기 발행 이력/이전 RGB만 전달한다. 상대 자기 카메라, 상대 발행 명령·메시지, 측정 관절, 접촉, 좌표, 지도, seed, 평가 진행률은 전달하지 않는다.

모델·문맥 생성기·변환기는 `world` 객체를 받지 않는다. 변환기 입력은 검증된 행동, 고정 profile, 자기 발행 명령 장부만이다. `capture()`/`apply()`가 반환하는 상태 묶음을 모델 메시지로 직렬화하지 않는다. 같은 프로세스의 객체 경계는 보안 샌드박스가 아니므로 코드 의존성 검토와 wire 재구성 감사를 함께 수행한다.

## 5. 첫 행동 어휘: 14개, 매번 하나

아래 수치는 구현 시작용 후보이며 최적값이나 검증된 물리 이동량이 아니다. development fixture에서 영상으로 확인한 뒤 전체 비교 전에 profile을 고정한다.

| 토큰 | 변환될 기존 raw 명령 |
|---|---|
| `BASE_FORWARD` | `drive(forward=0.05, turn=0, duration_s=0.3)` |
| `BASE_LEFT`, `BASE_RIGHT` | `drive(forward=0, turn=+0.1/-0.1, duration_s=0.3)`; 실제 좌우 부호는 development 영상으로 확인 후 고정 |
| `WRIST_INC`, `WRIST_DEC` | servo 3의 마지막 발행 목표에 ±50 pulse |
| `ELBOW_INC`, `ELBOW_DEC` | servo 4의 마지막 발행 목표에 ±50 pulse |
| `SHOULDER_INC`, `SHOULDER_DEC` | servo 5의 마지막 발행 목표에 ±50 pulse |
| `PAN_INC`, `PAN_DEC` | servo 6의 마지막 발행 목표에 ±50 pulse; 기존 `look`으로 발행 |
| `GRIP_OPEN`, `GRIP_CLOSE` | servo 1에 각각 2000 / 1500 pulse |
| `WAIT` | 기존 wait: 바퀴 정지; 관절 목표를 취소하거나 실제 파지를 확인하지 않음 |

INC/DEC는 펄스 부호의 뜻이다. 끝점의 위/아래 또는 화면의 좌/우를 보장하지 않는다. 고정 설명에는 기존 서보 역할과 부호를 명시한다. PAN은 팔과 손목 카메라를 함께 움직이는 기존 actuator이며, 카메라 장착 위치·FOV를 편집하는 기능이 아니다. raw 조건에도 동일한 동작 설명과 PAN 사용 권한을 준다.

첫 버전에는 후진, 측면 주행, 조합 행동, 자동 접근·집기·들기, 크기 선택, `DONE`이 없다. 현재 raw 정책의 허용 동작 범위를 확장하지 않는다.

### 발행 명령 장부

1. 실험 설정에 공개된 고정 초기 펄스를 fixture owner가 모든 조건에 똑같이 발행한다. 실제 관절을 읽어 초기값을 역산하거나 교사 파지 자세를 묵시적으로 사용하지 않는다.
2. 변환기는 같은 초기 발행값으로 시작한다. 이 setup 명령은 actor가 선택한 것이 아니므로 private 장부에만 넣고 H1/H2의 자기 발행 이력에는 넣지 않는다. 첫 round의 자기 이력은 두 인터페이스 모두 빈 배열이다. 이후 raw 목표와 이산 행동 변환 결과 중 actor가 선택해 실제 발행한 명령만 자기 이력에 기록한다.
3. 증분은 마지막 **발행 목표**에 더한다. 실제 도달 위치·보간 진행률·측정 관절을 읽지 않는다.
4. pulse 범위는 기존 500..2500으로 clamp한다. clamp가 일어나도 실제 한계 접촉이나 성공이라고 해석하지 않는다. 요청값·해석값·발행값·clamp 여부는 감사 로그에 보존한다.
5. 포화로 이동이 없어도 다른 행동을 자동 선택하지 않는다. 다음 RGB를 보고 모델이 선택한다.
6. WAIT는 과거 목표를 잊거나 상태를 동기화하지 않는다. reset 시에만 고정 초기 명령 장부로 재시작한다.

모델 출력 예시(신규 계약 제안):

```json
{"reason":"빔 근처에서 손목을 조금 조정한 뒤 다시 확인한다.","action":{"kind":"discrete","unit":"WRIST_INC"}}
```

숫자 인자·여러 unit·알 수 없는 토큰은 거부한다. 양쪽 출력 검증을 마친 뒤 함께 발행하므로 한쪽만 행동한 부분 round를 만들지 않는다. malformed 응답은 두 조건 모두 같은 정책으로 처리한다: 자동 재질문 없이 해당 episode를 policy-output failure로 끝내고 실패 및 비용에 포함한다. 네트워크 실패는 별도 infra error로 기록하고 원본을 보존한다. 첫 cohort는 SDK 내부를 포함해 자동 재시도 0회로 고정하고, 해당 episode를 대체 실행하지 않는다. 연속 2개 episode가 infra error이면 cohort를 중단한다. 복구 후 미실행 항목만 재개할 수 있으며, 완료/실패 항목은 덮어쓰지 않는다. 같은 fixture의 6조건 중 infra error나 평가 무효가 있으면 그 fixture 전체를 paired 분석에서 제외하고 제외 수·이유·모든 원시 결과를 공개한다. 제외 표본을 실패로 처리한 보수적인 전체 예정 표본 성공률도 별도로 보고한다. 실패/타임아웃 호출 비용도 포함하며 청구 여부 미확인은 unknown으로 남긴다. 새 재실험이 필요하면 별도 ID로 해당 fixture의 6조건 모두를 다시 실행하고 원 cohort 결과와 섞지 않는다.

## 6. 문맥과 공정한 비교

| | H0: 현재 RGB 2장 | H1: H0 + 자기 명령 4개 | H2: H1 + 이전 RGB 2장 |
|---|---|---|---|
| R: 기존 숫자 행동 | R0 | R1 | R2 |
| D: 14개 이산 행동 | D0 | D1 | D2 |

- 처음 계획의 순차적인 4조건 대신 2×3 요인 비교를 사용한다. D0-R0, D1-R1, D2-R2로 각 기억 조건에서 인터페이스 효과를 본다.
- H1/H2의 이력은 두 표현 모두 **실제 발행된 normalized raw 명령** 4개로 통일한다. D의 토큰→raw 매핑 설명은 고정 문서로 제공한다. 장부와 기억은 다르며, H0에서도 변환기 내부 장부는 필요하지만 모델에는 노출하지 않는다.
- H2는 바로 직전 같은 actor의 자기·top 영상 쌍만 더한다. 첫 round는 이전 영상이 없다. peer 움직임 때문에 전후 변화가 자기 행동의 인과 효과라는 보장은 없다.
- 기존 `learned` 시각 효과 추정은 6조건에서 끈다. 추가한다면 별도 축과 새 실험 ID가 필요하다.
- 작업·하드웨어 설명, 모델/추론 설정, 화면 크기, 물리 timestep, 초기 명령, 1초 실행 구간, round 예산, 정책 오류 처리를 맞춘다. 현재 task별 설명의 차이로 결과가 바뀌지 않도록 `grasp` 설명을 공통으로 고정한다.
- raw는 연속 범위와 drive 동시 전진/회전을 선택할 수 있고 D는 후보 집합이 작다. 따라서 R-D 차이는 **전체 제어 인터페이스 효과**이며 단어의 의미 효과만으로 해석하지 않는다.
- 후속 의미 표현 실험은 동일한 14개 변환기를 놓고 `WRIST_INC`와 설명이 붙은 임의 코드 `A07`을 비교한다. 실행 능력·장부·후보 수를 맞춰야 이름 효과를 분리할 수 있다.
- H2는 이미지가 많으므로 호출 수만 같아도 비용이 같지 않다. 1차 비교는 동일 물리/round 예산, 비용 제한 비교는 별도 보조 분석으로 구분한다.

## 7. 시각·동기화·성공 판정

한 round: 같은 물리 시점 RGB 고정 → 두 독립 VLM 요청 → 두 응답 검증 → 같은 SIM 시각에 발행 → 1초 물리 실행 → 다음 round. 늦은 모델을 기다리는 동안 물리는 진행하지 않는다. 첫 단계에서는 barrier 자체를 모든 조건에 공통으로 둔다.

평가기는 기존 조건을 유지한다: 빔 시작 대비 높이 ≥0.03 m, 두 로봇 각각 bilateral 접촉, 모든 보조 고정 제약 OFF, 0.1초 표본에서 연속 2초 유지. 이는 시뮬레이터 기준의 공동 파지 지표다. 실제 영상에서 바닥·주변 물체에 지지된 채 점수를 얻는 경우 등 판정 오류도 검토한다. 필수 접촉/제약/높이 필드 누락과 시간 역행은 평가 무효로 별도 보고한다. 표본 간격이 허용 범위를 넘으면 연속 유지 구간을 끊고 gap을 기록하며, 평가 무효를 보통의 정책 실패나 성공으로 숨기지 않는다.

1차 성공 레이블은 위 물리 지표를 통과한 episode 중 영상 검토에서도 외부 지지가 없는 것으로 확인된 경우다. 모든 물리 지표 양성 영상을 조건명/토큰/응답을 숨긴 채 두 검토자가 독립적으로 확인한다. qualifying 구간에서 빔이 바닥·환경·그리퍼 외 로봇 부위에 지지되면 최종 실패로 분류한다. 의견이 다르면 제3 검토자가 판정하며, 영상으로 확인 불가능하면 평가 무효로 남긴다. 원 물리 지표와 최종 레이블을 모두 보존한다. 이 검토 기준은 조건별 결과를 보기 전에 고정한다.

성공 시 자동 종료하거나 모델에 성공을 알리지 않는다. 종료는 고정 예산 또는 정책/인프라 오류로만 결정한다. 모델의 주장과 평가기의 성공은 별도로 기록한다. API 지연이 물리에 반영되지 않으므로 이 실험의 SIM 성공률을 실물 실시간 성공률로 보고하지 않는다.

## 8. 실험 규모와 개발/검증 분리

### 0단계: 인터페이스를 먼저 검증

- 모델 없이 각 토큰의 변환·반복·포화·reset·WAIT를 검증한다. action을 발행한 테스트이지 파지 정책 성공이 아니다.
- development 장면에서 토큰별 전후 RGB를 검사해 부호·동작 크기·PAN 효과를 확인한다. 팔 증분 후보 25/50/100 pulse 중 하나를 선택하고 양 로봇에서 점검한다.
- 30 rounds 안에 작은 명령으로 과제 수행에 필요한 움직임이 가능한지 점검한다. 불가능하면 숨겨진 매크로를 추가하지 않고, 예산/과제 시작 난도를 development에서 수정한 뒤 모든 조건에 동일 적용한다.

### 1단계: 개발 pilot

- development fixture 4개 × 6조건 = 24 episodes, 최대 30 rounds 기준 1,440 actor 호출.
- 목적은 경계·도달 범위·영상 품질·비용·오류 처리 점검이다. 성공률 우열의 최종 근거로 쓰지 않는다.
- seed만 다르다고 새로운 장면으로 세지 않는다. 기존 실행기는 로봇 배치를 덮어쓰므로, fixture owner가 초기 base 위치/방향·빔 배치를 명시적으로 바꾸고 저장한다. 카메라·FOV·물체 외관·마찰은 첫 비교에서 고정한다.

### 2단계: 고정된 전체 비교

- 별도 held-out fixture 30개 × 6조건 = 180 episodes. 접근 방향·거리·두 로봇의 비대칭 배치를 균형 있게 포함한다. 정확한 값은 fixture manifest에 저장하며 actor에는 주지 않는다.
- 30 rounds면 최대 10,800 actor 호출. development에서 60 rounds가 필요하다고 결정하면 먼저 실행기의 제한을 수정하고 예산을 재고정하며 최대 21,600 호출이다. 이 문서는 호출 실행 승인이 아니라 설계이며 이번 작업에서는 실행하지 않는다.
- 같은 fixture의 6조건 실행 순서를 무작위화하고 모델 버전·시각을 기록한다. fixture는 매 episode 동일하게 reset한다.
- 호출 수와 별개로 cohort 비용 상한을 실행 전에 설정한다. 파일럿에서 확인한 실제 usage로 예상 입력/출력 토큰을 계산한다. 과금 단가 또는 usage를 확인할 수 없으면 금액을 추정 확정값으로 보고하지 않는다.
- 비용 상한으로 일부 조건만 끝난 경우 부분 cohort임을 표시한다. 완료 조건만 골라 우승 조건을 선언하지 않는다.
- prompts, profile, fixture, 모델 설정과 실행 코드를 결과 열람 전에 고정/커밋한다. held-out 결과로 튜닝하면 새 개발 집합으로 취급하고 별도 held-out 평가를 만든다.

### 지표와 판정

1차 지표: fixture별 paired 공동 파지 성공 차이. 사전 지정 주 비교는 D2-R2, 나머지는 기억과 상호작용 분석이다. 30개 장면은 초기 평가 규모이며 통계적 검정력을 보장하지 않는다.

보조 지표: 최초 qualifying hold까지 SIM 시간, 종료까지 실제 시간, actor 호출/토큰 수, 실제 과금 확인 범위, 최대 높이·유지 시간, 정책 출력 오류, saturation, 제자리 명령 반복 및 역방향 진동. 단순 명령 반복은 실패의 원인이나 물체 이동 없음의 증거가 아니다. 반복 지표는 raw와 token 문자열 대신 normalized 발행 동작 기준으로 계산한다.

모든 episode의 최종 성공/실패와 infra 오류를 공개한다. 성공 episode 시간만으로 속도를 비교하지 않고 전체 예산/실패를 함께 보고한다. 성공률은 구간 추정, 조건 차이는 fixture 단위 paired bootstrap 또는 이진 paired 검정으로 분석하고 탐색적인 다중 비교를 표시한다.

엔지니어링 진행 기준(논문 유의성 기준과 다름): 입력 감사 전부 통과, 동작 해석·카메라 동일성 검증, 동일 cohort 완료, D2의 성공률이 R2보다 최소 10%p 높고 episode당 중앙 비용이 1.5배 이하이면 다음 운반 실험 후보로 삼는다. 차이의 불확실성 구간이 0을 포함하면 개선 확정이라고 보고하지 않는다. 둘 다 0이면 모델 크기를 먼저 늘리지 말고 관측 가능성과 행동 도달 범위를 진단한다.

## 9. 구현할 파일과 인수 기준

아래 신규 이름과 CLI는 **제안**이며 현재 존재하는 기능이 아니다.

| 파일 | 변경 범위 | 인수 기준 |
|---|---|---|
| 신규 `harness/camera_discrete_actions.py` | immutable profile, 14토큰, command ledger, raw 변환 | world/측정 의존성 없음; deterministic; robot별 격리 |
| `harness/camera_pair_policy.py` | `action_interface=raw/discrete`, 기존 mode와 독립 | default raw의 기존 요청·파싱·감사 회귀 보존 |
| `scripts/run_camera_pair_transport.py` | profile/fixture 선택, 공통 초기 발행, 양쪽 사전 검증 | 평가에서 actor로 값 이동 없음; 동시 snapshot/고정 slice 보존 |
| 신규 `scripts/run_camera_interface_cohort.py` | 6조건, 순서, 실패/비용 상한, resume manifest | 기존 결과 덮어쓰기 없음; SHA 고정; 부분 결과 명시 |
| `scripts/audit_camera_pair_inputs.py` | wire·이력·token/raw 변환 재구성 | 위조 이력·peer 영상·평가 상태 삽입 검출 |
| `scripts/review_camera_pair_cohort.py` | 2축 요약, paired 지표, usage 누락 | raw/semantic을 같은 기준으로 비교; 누락을 0원으로 간주하지 않음 |
| 관련 tests | 경계·장부·reset·타이밍·평가 격리 회귀 | 실제로 가능한 회귀 검증; 구현을 그대로 복사한 테스트 지양 |

추가 필수 검사: 고정 초기 펄스 누락 시 실행 전 오류, 첫 H1/H2 이력 비어 있음, 같은 fixture의 6조건에서 초기 상태 hash 동일, 불변 모델 geometry·카메라 장착/FOV hash와 fixture 초기 배치 hash를 분리(동작 중 손목 카메라의 world pose는 변할 수 있음), token→raw 재구성 일치, 한 actor의 오류 시 부분 발행 없음, 과거 이미지 순서, evaluator 파일이 없어도 요청 재구성 가능, runtime 종료 후 해당 세션 자식 정리.

구현 순서: (1) 변환기·프로파일과 offline 테스트 → (2) runner/policy 통합 및 작은 실제 영상 QA → (3) auditor/cohort 구현 → (4) 실행 SHA 고정 후 pilot → (5) 최종 cohort. 관련 CI와 실제 사용자 흐름을 구분해 보고한다. main 병합은 해당 PR의 사용자 승인 뒤에만 수행한다.

## 10. 후속 연구 연결

### 운반과 협력

공동 파지 결과가 준비되면 운반 목표 영역·물체 유지·놓기 평가기를 output-only로 추가한다. 중앙 VLM의 두 행동 공동 예측과 독립 두 VLM을 비교할 수 있지만 관측 범위와 호출 예산이 달라짐을 명시해야 한다. 메시지 협력은 현재 학생 입력 계약을 바꾸는 후속 설계로 다룬다. 첫 6조건에 몰래 추가하지 않는다.

### 교사와 학생

같은 14개 행동으로 GUI/교사 시연을 수집하고, `(자기 RGB, top RGB, 자기 발행 명령 이력) -> 행동 토큰` 학습 표적을 만든다. 교사는 승인된 범위에서 좌표·IK·접촉을 사용해 시연과 성공 레이블을 만들 수 있다. 학생 입력에서는 이를 제거한다.

기존 연속 교사 궤적을 토큰 이름으로만 바꿔 정답으로 저장하지 않는다. 이산 행동으로 분해한 경로를 실제 실행하며 중간 관측을 다시 수집하고 원 교사와 같은 성공을 유지하는지 확인해야 한다. training loss, 동일 시연 재생, 새로운 배치에서 독립 학생 성공을 각각 분리한다. 처음부터 새 학습/GPU 환경을 구축하지 않고 interface 비교 이후 필요성을 판단한다.

## 11. 기록과 완료 상태

구현 후 `experiments/<id>/`에 실행 SHA, profile/prompt/fixture hashes, 환경, 모델 버전, 6조건 manifest, 모든 성공/실패, 검토 범위, raw 경로와 해시를 기록한다. `outputs/<id>/`에는 실제 wire, RGB, 행동 토큰/발행 명령 장부, 평가 전용 로그, 영상과 usage를 보관한다. 인증 토큰·비밀 설정·인증 헤더는 저장하지 않는다. Google Drive는 프로젝트 지침에 따라 사용하지 않는다.

현재 완료: 논문-현재 코드 대조, 입력/실행 경계 설계, 행동 어휘, 6조건 비교, 비용 규모, 구현 인수 기준. 미완료: 구현, profile 시각 검증, 실험, 성능 주장. 이 문서는 실행 가능 설정 파일이나 성공 결과물이 아니다.
