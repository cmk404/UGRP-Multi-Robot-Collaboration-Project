## PR #170 — `zone-rgb-outcome`

- **[high · 확정] 평가 입력과 제안 훅에 교사 상태 의존이 남는다.** 평가기는 교사의 종료 시각을 관측 시작점으로 쓰고, 교사 `phase`로 자기 RGB 제공 여부와 `FOLDED` 명령값을 결정한다(`scripts/eval_zone_rgb_outcome.py:131–168,221–239`). 제안 훅도 교사 실행기가 idle이 된 뒤에만 판정한다(`experiments/2026-09-25-zone-rgb-outcome/README.md:156–177`). 따라서 RGB가 같아도 정답 기반 조기 종료가 관측·재질문 시점을 바꾼다. **수정:** 관측·판정 시계를 교사 종료와 분리하고 실제 자기 발행 명령을 보존해 사용한다. **이 훅만으로 L4는 제거되지 않는다.**

- **[high · 확정] 움직이지 않은 가림을 ‘보이는 빈 출발지’로 오인한다.** `point_visibility()`는 before/after 고리 변화가 적으면 보인다고 판정한다(`harness/zone_rgb_outcome.py:160–195`). 배정 전부터 로봇이 출발지를 가리고 계속 정지하면 변화량은 0이다. 이때 동료의 같은 색 상자가 목표에 나타나면 `delivered`, 신뢰도 0.95가 된다(`:284–305`). **수정:** 변화 없음과 가림 없음을 구분하고, 출발지 가시성을 입증하지 못하면 미확정으로 남긴다. 팀 화물도 중심점만 검사하므로 들림·잘못된 yaw·영역 밖으로 나온 footprint를 완료로 판정할 수 있다(`:147–150,252–256`).

- **[high · 확정] 공개 `commit()`과 평가의 확정 정책이 다르다.** 모든 결과가 저신뢰여도 `commit()`은 마지막 `delivered`를 반환하고, `receipt()`는 성공 문구를 만든다(`harness/zone_rgb_outcome.py:344–366`). 평가기만 이를 별도로 `not_seen`으로 바꾼다(`scripts/eval_zone_rgb_outcome.py:475–493`). 실제 synth-test 두 사례가 이 보정에 의존한다. **수정:** 미확정 상태를 모듈 API에서 명시적으로 반환하고, 영수증·러너·평가가 같은 정책을 사용하게 한다.

- **[medium · 확정] 재실행이 기존 증거를 덮어쓴다.** 동일 출력 경로를 허용한 뒤 영상·입력·정답·점수 파일을 다시 쓴다(`scripts/eval_zone_rgb_outcome.py:205–213,261–273,366–396,509–510`). 같은 명령을 재실행하면 이전 해시가 가리키는 원본이 사라진다. **수정:** 실행별 새 디렉터리를 요구하고 기존 산출물이 있으면 중단한다.

**평가 해석:** 모듈·commit 임계값을 test에 맞춰 사후 수정했다는 증거는 없다. 그러나 test에는 실제 운반 중 낙하가 0건이고, 교사 종료 이후의 재렌더 영상만 평가했다. 픽셀 차이 검사는 원본 영상에서 판정도 같다는 검사가 아니다. 따라서 `false delivered=0`을 일반적 안전성으로 확대할 수 없다. README 확정 행렬의 `still_at_source=38`도 `results.json:351–360`의 **39**와 다르다.

## PR #172 — `zone-dialogue-ko-pilot`

- **[high · 확정] 중단된 대화 창을 재개하면 원시 wire를 덮어쓴다.** 완료 여부는 `dialogues.json`의 완성된 창으로만 판단하고, 창 내부에서는 기존 `calls.jsonl` 호출을 재사용하지 않는다(`scripts/pilot_korean_dialogue.py:297–323,347–362`). 3턴 뒤 중단하고 재실행하면 같은 call ID와 파일명으로 다시 호출하여 이전 wire/response를 덮어쓴다(`:181–194`). **수정:** 턴별 체크포인트·기존 호출 검증을 추가하거나 새 실행 ID를 부여한다.

- **[medium · 확정] README의 일부 권고·인과 주장이 결과보다 강하다.** 충돌 감소를 직렬화의 효과로 단정하지만, 같은 프롬프트·언어에서 동시/직렬을 비교하지 않았다(`experiments/2026-09-25-zone-dialogue-ko-pilot/README.md:59–72`). 출력 256토큰 권고도 plan_first까지 적용하면 부족하다(`:82`): V2 단일 턴 6건이 이를 넘고, 유효 응답 하나는 365토큰이다(`results.json:5902–5918`). **수정:** 직렬화는 가능한 설명으로 표현하고, 토큰 상한은 창/계획 모드를 구분해 검증한다.

- **[low · 확정] 대화 행위 규칙이 언급과 실제 행위를 혼동한다.** `propos`는 “Accepted proposal”도 `propose`로, `agree`는 “disagree”도 동의로 분류한다(`harness/zone_dialogue_metrics.py:63–84`). 실제 V0 수락·대기 발화에도 제안 라벨이 붙는다. **수정:** 단어 경계·부정·발화 기능을 구분하고 영어까지 포함한 수동 표본으로 검증한다.

기본 보존 검사는 양호하다. **124건의 원시 wire 해시와 이미지 기록이 일치했고**, 단일 턴 user JSON도 원본과 같았다. 새 조정 규칙·발화 대본 추가는 발견하지 못했다. 한글 비율의 literal 제외와 README의 주요 수치—V2 19/20, claim 동일 6/10—는 결과와 맞는다. 다턴 요청은 명시적으로 request ID와 대화 문맥을 바꾸므로 요청 전체의 바이트 동일성 대상은 아니다.
